# 金融营销材料合规审查 Skill

一个跑在 WorkBuddy 上的 Agent Skill，对基金、资管、理财产品的营销宣传材料做发布前合规审查，输出可追溯到法条原文的问题清单。

规则库 43 条规则、法条索引 39 个条目，全部处理在本地完成，零第三方依赖。

---

## 一、要解决的问题

资管机构的营销材料在对外发布前必须经合规审查。现状是合规人员逐字读稿，凭经验对照几十份监管文件判断。这件事的痛点不在"难"，在于三点：

1. **量大且重复**：新品发行、公众号推文、路演材料、海报，一家中型基金公司每周几十份。
2. **规则分散且分层**：从《广告法》到中基协自律规则，散落在十几份文件里，且公募、私募、资管计划、理财产品适用的条款不同。
3. **规则会变**：《金融产品网络营销管理办法》2026 年 9 月 30 日施行，一旦生效，存量材料里的"低风险""秒到账"全部触线，需要批量重扫。

同时有两条硬约束决定了技术方案：

- **材料内容高度敏感**。未发布的产品信息属于内幕信息（MNPI），不能出网、不能过第三方 SaaS。
- **合规结论不能由机器下**。合规意见书要签字担责，工具只能做第一道筛子。

所以这个 Skill 的定位是：**本地运行的、可追溯到法条原文的、辅助人工的事前审查工具**，不是自动审批器。

## 二、整体架构

```
                     待审材料（md / txt / 由 Agent 解析的 pdf、docx、pptx）
                              │
                              ▼
                  ┌───────────────────────┐
   四维上下文  ──▶ │   scan_rules.py       │  CLI：参数解析、上下文推断、结果渲染
   产品/受众/      └───────────┬───────────┘
   载体/机构                   │
                              ▼
                  ┌───────────────────────┐
                  │   rule_engine.py      │  规则加载、作用域路由、文本预处理
                  │                       │  五类检测器、排除上下文、重叠去重
                  └───────────┬───────────┘
                              │ 读取
                              ▼
        references/rules/*.json  ──ref_id──▶  references/legal-index.md
        （43 条规则，四个文件 + 共享模式组）                  （39 个法条条目，含原文与核实状态）
                              │
                              ▼
                    JSON 输出（findings 四元组）
                              │
                              ▼
                  ┌───────────────────────┐
                  │  Agent 语义研判        │  整体误导、变相承诺、风格漂移
                  │  + 报告渲染            │  数据矛盾、术语未解释
                  └───────────┬───────────┘
                              ▼
                        待复核清单 ──▶ 合规人员判定
```

确定性扫描与语义研判是两层，各管各的：能被规则表达的交给规则，规则表达不了的交给 Agent。不让 LLM 去做关键词匹配（不稳定），也不指望正则去理解"通篇只讲收益不讲风险"（做不到）。

## 三、规则库全貌

### 3.1 按文件划分

规则按"检查什么"而非"违反哪条法"分文件，因为同一条法条可能派生多类检查，而使用者找规则时是按现象找的。

| 文件 | 检查内容 | 规则数 |
|---|---|---|
| `banned-expressions.json` | 材料中不该出现的表述 | 13 |
| `performance-display.json` | 业绩数据的展示方式 | 14 |
| `mandatory-elements.json` | 必须出现的要素与法定声明 | 11 |
| `format-presentation.json` | 排版与呈现形式 | 5 |

### 3.2 四个分类维度

每条规则同时具备四个正交属性，这是整套设计的核心。

**判定类型（verdict）** —— 决定报告怎么写，也决定谁来拍板：

| 取值 | 数量 | 含义 |
|---|---|---|
| `violation` | 23 | 命中即违规，直接列入报告 |
| `manual_review` | 15 | 需上下文或外部数据判断，工具只标位置 |
| `advisory` | 4 | 无条款依据的建议，不得表述为违规 |
| `evidence_required` | 1 | 法条限定"未提供客观证据时"才违规 |

`evidence_required` 只有一条（BAN-005），因为法条里明确写"在未提供客观证据的情况下"的表述本就稀少。引擎会检查命中位置附近有没有数据出处标注，有则自动降级。

**依据类型（basis）** —— 区分"法律说的"和"行业习惯"：

| 取值 | 数量 | 处理方式 |
|---|---|---|
| `statutory` | 40 | 挂条款号，报告中引用法条原文 |
| `industry_practice` | 3 | **禁止挂条款号**，报告中必须标注"无现行条款依据" |

这个区分不是洁癖。市面上大量合规工具仍在用证监会公告〔2008〕2 号的禁用词表（净值归一、首只、最大、最好、最强、避险），而该文件已被证监会公告〔2020〕59 号第二十条明文废止。把废止文件的词表当法条引用，等于给合规人员一个假的举证依据。本库保留这些词的检查（行业惯例仍有参考价值），但强制标注无条款依据，校验脚本会拒绝给 `industry_practice` 规则挂条款号。

**生效状态（status）** —— 处理新规过渡期：

| 取值 | 数量 | 说明 |
|---|---|---|
| `active` | 41 | 现行有效 |
| `pending` | 2 | 已发布未生效，报告中单独分节 |

两条 `pending` 规则（BAN-010、PERF-013）依据《金融产品网络营销管理办法》，2026 年 9 月 30 日施行。这两条是"存量材料批量重扫"场景的直接抓手。

**严重级别（severity）**：red 8 条、orange 30 条、yellow 5 条。

### 3.3 五类检测器

| 类型 | 数量 | 机制 |
|---|---|---|
| `keyword` | 14 | 正则匹配，支持排除上下文 |
| `manual` | 12 | 触发词命中后标记位置，交人工研判 |
| `conditional_required` | 9 | 若出现 A 则必须出现 B（如登载业绩则须有免责声明） |
| `required` | 5 | 必须出现某要素 |
| `numeric` | 3 | 提取数值并做区间判断（如业绩区间是否满 6 个月） |

`conditional_required` 数量仅次于 keyword，反映了这个领域的规则特点：大量条款不是"禁止说什么"，而是"说了 A 就必须同时说 B"。纯关键词方案覆盖不了这类规则，这也是本方案与通用敏感词工具的分界线。

### 3.4 作用域路由

同一句话在不同场景下适用的法条不同，所以每条规则声明四维作用域：

| 维度 | 取值 |
|---|---|
| `products` | public_fund / private_fund / am_plan / wealth_mgmt |
| `audience` | public / specific |
| `media` | print / online / video / audio |
| `institutions` | fund_manager / securities_firm / bank / wealth_subsidiary |

最典型的例子是 BAN-001 与 BAN-002：都是"承诺保本保收益"，但公募依据《广告法》第二十五条与《暂行规定》第十五条，私募依据《私募投资基金监督管理条例》第二十条（位阶为行政法规）。二者在"避险"一词上还有实质差异——私募场景明文禁用，公募场景无现行依据。合并成一条规则就会引用错法条。

上下文未提供时，相关规则跳过而非默认适用。宁可漏报，不在信息不足时误报，报告中会说明哪些规则因此未被应用。

这条原则**四个维度一视同仁**，尤其不能对产品类型网开一面。早期实现里 `media` 与 `institutions` 缺失即跳过，而 `products` 与 `audience` 缺失时放行，理由是"后两者通常总能确定"。但只要 `--product` 没传，带 `products` 限定的规则就会全部生效——私募与理财的专属规则落到公募材料上，报告会向公募材料引用《私募证券投资基金运作指引》这类根本不适用的条款。错误的法条引用比漏报危险得多，合规人员拿它去举证会直接失分。现在四个维度统一为缺失即跳过，代价是不传 `--product` 时 39 条规则失效、扫描形同虚设，但这个后果是显式的：跳过原因会写进 `stats.skipped_rules`，报告必须如实说明。

### 4.2 核实状态

每个法条条目标注核实状态，取值三档：

| 状态 | 数量 | 含义 |
|---|---|---|
| 已核实原文 | 33 | 从官方来源取得条款完整原文 |
| 已核实存在 | 6 | 确认条款存在，但未从官方来源取得完整原文 |
| 未能核实 | 0 | 无法确认，**禁止被规则引用** |

标注"已核实存在"的 6 条中，有 3 条附了具体说明，例如：

- `N-BM-16`（业绩比较基准指引第十六条）：条文经第三方站点转载核对，建议以证监会官网附件 PDF 复核后升级
- `SA-SEC-22`（中证协适当性指引第二十二条）：内容经华宝证券、甘肃证券期货业协会两处转载核对一致，未从中证协官网取得原文
- `SA-AMAC-SUIT-38`：条款号经多来源交叉印证，未能从 amac.org.cn 取得正文

保留这个字段而不是一律标"已核实"，是因为报告里的法条原文会被合规人员拿去做举证依据。来源不够硬的必须让人知道。

### 4.3 时效性处理

法条索引开头有一节"时效性警示"，处理两类问题：

**已废止但仍在流传的规则。** 证监会公告〔2008〕2 号已被 2020 年 59 号文第二十条明文废止，但其禁用词表和"5 个工作日内报证监局备案"的流程要求仍在大量资料中流传。现行《暂行规定》没有向证监局报备的要求，只要求内部合规审查、出具合规意见书、存档备查。

**已发布未生效的规则。** 《金融产品网络营销管理办法》2026-09-30 施行，规则标 `pending`，报告单独分节。《公开募集证券投资基金销售行为规范》仍是征求意见稿，不入规则库。

## 五、关键设计决策

### 5.1 规则外置为 JSON，而非写死在代码里

合规规则的变更频率远高于引擎逻辑。规则外置后，新增一条规则是加一个 JSON 对象，不需要读 Python 代码，也不需要改引擎。业务人员可维护是这个方案能长期存活的前提。

选 JSON 而非 YAML 是因为目标环境是 Python 3.9.6，`json` 在标准库里，`pyyaml` 需要额外安装。为一个格式偏好引入依赖不划算。

### 5.2 每条规则内嵌测试样例

每条规则带 `tests.match` 与 `tests.no_match`，`validate_rules.py` 会全部执行。当前 129 个测试用例。

这是整套设计里最关键的一环。合规规则的正则天然容易过度匹配，改一处正则很容易在别处引入误报，而误报在这个场景下的代价极高——见下节。没有回归测试，规则库迭代几轮之后就没人敢改了。

校验脚本同时检查：字段合法性、枚举取值、rule_id 唯一性、正则可编译性、`ref_id` 在法条索引中是否存在、`industry_practice` 规则是否挂了条款号。**校验不通过不得交付。**

### 5.3 误报比漏报更危险

开发时用一份**完全合规**的公募材料做基线测试，抓出三个误报，全部属于同一类：把法规强制要求写的句子判成了违规。

| 命中 | 原文 | 实际性质 |
|---|---|---|
| 没有风险 | "…也不表明投资于本基金没有风险" | 证监会要求的法定注册声明 |
| 预期收益 | "其预期风险与预期收益高于债券型基金" | 《运作管理办法》的风险收益特征标准句式 |
| 基准收益率 | "业绩比较基准收益率" | 法定允许的基准列示方式 |

这类误报比漏报危险得多：合规人员照着报告改，材料会从合规变成缺失法定要素。修复方式是 `exclude_context` 机制（命中点前 12 字符窗口内出现排除模式则跳过）与正则负向断言，并把三个句子写进回归测试、在规则 `notes` 里注明不得移除。

所以样本库里合规样本与违规样本同等重要。8 份样本的完整基线见 `examples/README.md`，其中三条硬约束是回归的红线：

| 样本 | violation | 用途 |
|---|---|---|
| 公募合规版 | **0** | 误报基线 |
| 公募边界表述版 | **0** | 由「表面像违规、实际合规」的表述构成，规则库精确度的核心检验 |
| 私募合规版 | **0** | 私募场景误报基线 |
| 公募违规版 | 17 | 检出基线 |
| 私募违规版 | 10 | 公私募分路由验证 |

边界表述样本在引入时抓出过两个真实缺陷：一是 REQ-009 把「货币市场基金」作为裸关键词，而《运作管理办法》要求的风险收益特征标准句式（"其预期风险与预期收益高于债券型基金与货币市场基金"）必然包含该词，导致**每一份合规的混合型、股票型基金材料都会触发违规**；二是「不得以任何方式暗示保本」这类否定表述未被排除上下文覆盖。两者均已修复并纳入回归测试。

同期还发现引擎会扫描 Markdown 注释。起草阶段的批注中引用违禁词原文（如"此处不得出现保本表述"）是常见写法，扫描它们只产生噪音，现已在预处理阶段将注释替换为等长空格——用等长空格而非删除，是为了保持字符偏移量不变，使行号与原文片段仍然准确。

### 5.4 四种判定类型，而非"违规/不违规"二分

早期版本只有违规与否。问题是大量规则本质上无法由文本判定——"销售机构标注的风险等级不得低于管理人评级"需要查管理人的官方评级，"业绩比较基准须与基金合同一致"需要查基金合同。这些既不能报违规（没依据），也不能不报（确实是检查项）。

拆成四类之后，每类在报告里的呈现方式和责任归属都不同，`manual_review` 明确写"须由合规人员核验"。这比给出一个假的确定性结论要诚实。

### 5.5 报告由 Agent 渲染，不用硬编码模板

引擎输出 JSON，每条 finding 带齐四元组：原文引用与位置、法条依据（全称+条款号+原文）、处罚案例、修改建议。报告由 Agent 基于 JSON 组织。

理由是报告的呈现需求是变的——有人要按严重度排序，有人要按材料章节排序，有人要导出给业务方看简版。硬编码模板每变一次需求就改一次代码，而 Agent 渲染只需改 `SKILL.md` 里的指令。

代价是格式稳定性略低。用 `SKILL.md` 里的报告结构规范约束，并强制要求每一项必须带法条原文、不得使用"违反相关规定"这类模糊表述。

### 5.6 全本地运行

材料内容不出网，不调用任何外部 API。这是 MNPI 敏感性的直接要求，也是这类工具能进合规部门的前提。

零第三方依赖同时降低了部署门槛：目标环境有 Python 3.9.6 即可运行，不需要 pip install，不需要联网装包。

### 5.7 报告可复算：规则库指纹

扫描结果带 `rule_set.fingerprint`，覆盖全部规则文件与法条索引的内容哈希。

合规报告要存档备查。若干月后被追问某项认定的依据，必须能取回当时的规则与法条原文重新复算——如果只知道"某次扫描报了 17 项违规"却不知道基于哪一版规则库，这条审计链就是断的。法条索引也纳入指纹：法条原文的任何改动都会改变报告内容，只对规则文件取哈希不够。

### 5.8 共享词表：副本一旦存在就一定会漂移

公募、私募、理财三条保本规则的依据不同——分别是《暂行规定》第十五条、《私募投资基金监督管理条例》第二十条（行政法规位阶）、《广告法》第二十五条——但它们禁止的表述形态高度一致。最初的做法是三份词表各自维护，结果如实地演示了副本的下场：私募规则少了「本金安全」「没有风险」「旱涝保收」等 6 个表述，而这些恰恰落在位阶更高的行政法规射程内；同时规则注释白纸黑字写着「与公募规则的唯一差异是避险一词」，把这个错误固化了下来，后续维护者不会再去核对。

129 个内嵌测试完全查不出这类问题——测试是按规则手写的，没人会想到给私募规则补一条「本金安全」的用例。这说明**测试只能防住你想到过的失效，防不住结构性的重复**。

现在三条规则引用同一个 `@guaranteed_return_core`（见 `references/rules/_shared-patterns.json`），产品特有的表述各自追加。BAN-002 的注释"唯一差异是避险"至此才名副其实。三份逐字相同的 `exclude_context` 同样合并为 `@negation_context`。引用未定义的组会直接报错而非静默跳过。

### 5.9 静默失效被当作硬故障处理

两类失败在合规场景比崩溃更危险，因为它们让用户以为"已经查过了"：

**正则编译失败**。一条规则的某个模式写坏时，扫描仍会正常返回结果，只是少查了一部分内容。现在扫描入口会预先扫出所有无法编译的模式并计入 `stats.pattern_errors`，`SKILL.md` 要求此时中止出具报告。

**编码识别失败**。国内金融机构存量材料大量是 GBK/GB18030，早期实现按 UTF-8 硬读会抛未捕获的 `UnicodeDecodeError`。现在按 utf-8-sig、gb18030、utf-16 顺序回退，并在结果中标注实际识别到的编码。顺序不能颠倒：gb18030 几乎能解码任意字节序列，排在 UTF-8 之前会把正常的 UTF-8 文本解成乱码。

## 七、已知边界

这些是当前明确做不到的，不打算用含糊表述掩盖：

1. **不做版式与视觉审查**。字号、颜色对比度、风险提示是否"醒目"这类要求（《暂行规定》第十二条）无法从纯文本判断，FMT-004 只能定为 advisory。
2. **不校验外部事实**。基金合同约定的业绩比较基准、管理人官方风险等级、基金经理管理的全部产品清单，都需要接入外部数据源才能真正校验，当前全部落在 `manual_review`。
3. **视频与音频只能审脚本**。FMT-003 的 5 秒风险提示时长需要材料中标注时长信息，无法从成片直接测量。
4. **整体印象类违规依赖 Agent 语义研判**，稳定性弱于规则层，不保证可复现。
5. **规则覆盖面以公募基金为主**。适用规则数：公募 34 条、私募 20 条、资管计划 13 条、理财产品 8 条。资管计划与理财产品仍偏薄，后续需补充。
6. **法规时效需人工维护**。规则库不会自动感知新规发布，`legal-index.md` 的核实时间需要定期更新。
7. **尚未在真实营销材料上做过评测**，precision / recall 暂无数据。当前基线来自 8 份自建样本，覆盖 43 条规则中的 39 条，详见 `examples/README.md`。
8. **条件必备类规则只做全文存在性判断，不校验位置关联**。这是当前最需要正视的漏报面：PERF-004 要求"展示业绩须同时登载业绩比较基准"，实现上只检查全文是否出现过"业绩比较基准"。因此任何材料只要在页脚放一段含"数据来源""业绩比较基准""过往业绩不预示未来"的标准免责声明，PERF-004、PERF-006、REQ-002、REQ-003 就会一并通过，无论正文里的业绩怎么展示。而法条原文写的是"同时登载"（N-AD-04）、"以显著方式特别声明"（N-AD-06），本身含位置与关联性要求。补法是给 `conditional_required` 增加 `proximity` 约束（同段落 / 同 N 字符 / 同表格），纯文本下先按空行切段近似。在此之前，**这几条规则的"通过"不足以作为合规依据**。
9. **引擎自身没有单元测试**。129 个内嵌用例保护的是规则词表，`dedupe_overlapping`、`is_excluded`、`mask_comments`、`scope_skip_reason` 这些引擎函数没有直接覆盖，而它们的缺陷会同时影响全部 43 条规则——本轮就是靠外部评审而非测试发现了区间合并与数值去重两个缺陷。另外内嵌测试走的是 `evaluate_rule`，不经过 `mask_comments` 与 scope 路由，这两个机制目前处于零测试覆盖状态。

## 八、使用方式

### 安装

```bash
ln -sfn /path/to/fin-marketing-compliance-review ~/.workbuddy/skills/fin-marketing-compliance-review
```

用符号链接而非复制，规则库改动即时生效。

### 命令行调用

```bash
python3 scripts/scan_rules.py \
  --file examples/sample-public-fund-violating.md \
  --product public_fund \
  --audience public \
  --media online \
  --institution fund_manager \
  --json
```

四个上下文参数均可省略，省略时对应规则跳过。

### 校验规则库

```bash
python3 scripts/validate_rules.py
```

任何规则改动后必须执行。

### 新增规则

先读 `references/rules/SCHEMA.md`，按位置放进对应的四个 JSON 文件之一，必须包含 `tests`，法条依据必须在 `legal-index.md` 中有对应 `ref_id`。改完跑校验。
